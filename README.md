# 穿搭推荐规范规则原型

这是一个可运行的逻辑原型，用来验证：用户输入具体改变哪些穿搭结果、多条关系怎样共同生成 2-3 个完整穿着方案，以及规则修改后如何同步影响案例运行结果。

## 两个页面

- `index.html`：案例运行。选择场景、肤色与发色、身体比例、脸型、风格偏好、目标和明确边界，直接查看输入条件与完整穿搭方案。
- `rules.html`：规则管理。总览直接读取规范字段与因果注册表，以 29 个输入字段 × 21 个输出字段展示完整影响矩阵；纵向按四类输入分组，横向按穿着框架、服装样式、鞋包配饰、穿着约束、颜色搭配分组。点击影响单元格会携带具体输入与输出上下文进入相应关系配置。

两个页面以规范数据和规范规则引擎为业务主路径。`rules-data.js` 只保留服装组件、色板和展示文案资源，`rule-engine.js` 负责把规范结果装配为可视候选方案：

- `canonical-data.js`：由 `docs/garment` 注册表生成的浏览器只读数据；
- `garment-objective-profile-registry.json`：温度与环境快照的客观组合效果基准，提供估算范围和有限校准，不写死固定层数或单品；
- `canonical-input-adapter.js`：29 项规范输入归一化及旧数据兼容层；
- `canonical-rule-engine.js`：执行 93 条基础矩阵及已批准修饰规则；
- `canonical-output-adapter.js`：将规范层数、袖长、外层、材质、领口、廓形、腰线、穿着约束、对比度与色彩对象映射到现有候选方案。

当前迁移已经完成。案例运行、可展开的 27×21 规则总览、单项规则/协同矩阵配置和发布存储共用规范字段、矩阵与修饰规则；旧推导规则不会在规范运行时执行。

页面同时提供“旧版回退 / 效果等价”双轨开关。效果等价模式使用V3候选独立运行时并作为默认结果；旧版回退继续保留已发布的V2规则，用于发布后的只读回退验证。V3规则工作台的草稿和发布版本使用独立存储，发布后只影响效果等价模式。

## 本地访问

静态服务地址：

- 案例运行：`http://127.0.0.1:4177/index.html`
- 规则管理：`http://127.0.0.1:4177/rules.html`

无需启动服务时，可直接打开单文件版：

- `garment-recommendation-standalone.html`

单文件版已内嵌样式、规则数据、推荐引擎和案例交互。更新原型源文件后可重新生成：

```powershell
node build-standalone.js
```

规范注册表变化后，先重新生成浏览器数据，再构建单文件版：

```powershell
node build-prototype-canonical-data.js
node build-standalone.js
```

如需重新启动服务：

```powershell
node serve-prototype.js
```

原型不依赖后端。草稿、发布版本和最近一次演示输入保存在浏览器 `localStorage`。

## 当前逻辑

- 温度是近期最低至最高温度的范围，生成客观组合效果画像；层数、袖长、外层和材质由单品能力池自动排列组合，温度分支不再直接写死固定层数或单品。下装形态由规范方案形态与版型输出决定，不再从袖长伪推导。
- 身材情况用身材比例和 H/O/X/A/Y 轮廓沟通；脸型单独输入，只影响领口和脸部周边细节。
- 场合定义使用边界；风格定义款式语言；正式程度定义服装完成度；潮流程度定义版型比例和细节强度。四者独立输入，再共同约束完整搭配。
- 风格切换会改变具体上装、外层、下装、整体轮廓、款式细节和图案纹理，不是只改方案名称。
- 颜色方案直接绑定上装、外层、下装或点缀位置，不输出与服装分离的色卡结论。
- 同一近脸安全色、全身对比度和色彩配比可以匹配多条可渲染色盘，使三个候选既有款式差异，也有配色差异。
- 潮流不再使用固定的高低等级，而是动态维护的潮流方向。每个方向包含理念来源、适用时间、服装路线、廓形比例、材质和细节映射。
- 表达强度只有在选定潮流方向后出现；切换潮流方向必须改变具体服装或版型内容，不能只改变说明文案。
- 腰线、线条和比例属于服装版型属性，不是独立推荐模块。
- 预计上身效果由服装款式、版型比例、细节强度和颜色关系共同生成，只作结果解释，不作为单独配置对象。
- 案例页不展示内部连续指数，只呈现完整组合和通俗搭配考量；规则工作台的客观分支才展示范围基准与校准偏移。
- 规则主表固定为场景条件、个人特征、风格偏好、目标边界四个输入分组；目标与边界默认聚合为两个入口，展开后逐项恢复注册表中的 29 个原子输入字段。
- 规则配置区分“单项规则”和“协同矩阵”。单项规则按输入项和输入取值导航，每个分支只有一个输入条件；气温×场合、肤色底调×发色深浅、横向轮廓×腿身分布×骨架量感只在协同矩阵中出现。
- 一件式候选独立展示裙型、领口、腰部、裙摆、袖长和外搭；近脸色谱展示首选、平替和避开三层；鞋履归入完整穿着，装饰配件归入进阶选配。
- 五类受控花色为海魂条纹、威尔士亲王格、千鸟格、法式波点和小碎花，每套候选最多显示一个主要花色。
- 规则管理分为“规则总览”和“规则配置”两个工作模式；总览单元格可直接跳转到对应配置。总览只回答“输入影响哪些结果”，配置页只维护当前关系的条件、影响结果、具体处理和理由；关系导航使用按钮，且脸型配置只显示脸型条件与领口结果，避免跨模块误配。
- 多个输入的中间计算收在“计算方式”中，默认折叠，不作为新的顶层规则。
- 每条关系明确影响范围；未列入范围的服装属性不会因为这条关系改变。
- 每次输出 2-3 个完整候选，并提供本套如何落实、未验证项、验证方式和失败条件。

## 边界

- 当前效果决策不使用湿度、室内外、活动强度、时长、光线、角色和观察者。
- 预算、品牌、新旧款、库存和护理条件属于商品匹配层，不进入当前效果路线。
- 不使用置信度决定是否出结果；缺少外观或身体事实时标记“需验证”。
- 当前不执行图片识别。正式接入图片后，识别结果仍需用户确认，再作为输入事实。
- 商品尺寸、纸样、面料厚度、织法、垂坠度和蓬胀度会改变实际效果，因此方案是可验证的预计结果，不是试穿结论。

## 验证

```powershell
node verify-prototype.js
```

自动验收覆盖：顶部导航对齐、温度和脸型联动、潮流真实服装变化、三套配色差异、单项规则与协同矩阵隔离、目标边界聚合与展开、一件式专属组件、三层色谱、鞋履与选配分层、五类花色、规则发布与跨页面同步，以及 1440×900 和 390×844 视口。

验收脚本在本地服务未启动时会临时启动服务，并在结束后自动关闭；已存在服务时直接复用。V3验收还覆盖候选独立输出、四级规则导航、动作目标与数值编辑、草稿保存、影子发布及发布值进入案例运行时。
